Where the time went, in plain words

For a slow click, tap or key press in a React app, it shows where the time went and names the component or handler.

Names the code

The component or handler most likely behind the slow interaction, in your own names.

Splits the time

Waiting, working and updating the screen, so you know which of the three to fix.

Sees what INP misses

A second React render that landed after the paint is joined to the click. INP doesn't count it, and people still wait for it.

Fits the tools you have

It rides on web-vitals attribution, or on the INP event OpenTelemetry already sends.

Says "most likely"

Every blame is marked measured or inferred, and the sentence says so when it is guessing.

A development tool first

The Vite plugin and the Next.js wrapper leave it out of production builds unless you turn it on.

A badge in the corner, a panel when you need it

  • A badge you can ignore

    A small dark badge sits in the corner and has no number until you interact. Then it shows the page's INP so far in milliseconds: green at 200 or under, amber up to 500, red above.

  • A panel of the slow ones

    Click the badge for the recent slow interactions, newest first. Each row names the component or handler and splits the time into waiting, working and updating the screen.

  • A row that explains itself

    Click a row for the whole explanation in plain sentences, including what React rendered after the paint and which components it was.

  • The same report in code

    Everything on the panel is also a report your code can read with onInteraction, so it can go to the tools you already use.

With web-vitals

The React side added to web-vitals' INP attribution, sent to Sentry or to GA4. One option on onINP, and the component path lands where web-vitals puts a CSS selector.

It needs web-vitals 5.1 or later. generateTarget needs no install() and never throws. attributeINP(metric) adds a react field with the blame, its confidence, the handler and the hot path. Sentry metrics need Sentry 10.25 or later.

Component names in production need the displayName transform from the Next.js wrapper, the Vite plugin or the loader. Without it a path reads a > b (button.tile).

Read the web-vitals guide

With OpenTelemetry experimental

The blame added to the INP event, in OpenTelemetry, Honeycomb, Elastic. It lands as react_inp_blame.* attributes, so you can group and filter on it beside the INP value. Export names and attribute names can change in any minor release, 1.x included.

This route needs the library running in production, so turn it on there and sample it. With the defaults every record says react_inp_blame.status: not-installed. Install the library before the telemetry setup, and put the processor first in the list.

Embrace and Grafana Faro have setups too. The entry sends component, handler and script names and numbers, never an element's text, target.label or a verdict sentence.

What you see

This is the library's real panel, for a click on login in the demo. The report shows a 400 ms interaction, about 399 ms of it in the handler, and a React render that landed after the screen updated. INP didn't count that later render.

Without the timeline it is easy to investigate the render and miss the handler. The panel says most likely where it is guessing, and a profiling build of React gives exact numbers.

It can be wrong. A component name is a lead to investigate, not proof that the component caused the delay.

How it works

It reads what the browser and React already expose, and joins the two. No component needs to change.

  1. It listens to the browser

    Event Timing gives each interaction's duration and its three phases. On Chromium 123 and later, Long Animation Frames adds which scripts ran and how much forced layout they caused.

  2. It reads React's fiber tree

    Through the hook React exposes for developer tools, it walks each commit and counts what rendered. It checks the shapes it reads and stops cleanly outside react-dom 17 to 19, with one warning.

  3. It joins them and picks a blame

    The blame is a render, a handler, a layout, a script, a hydration, waiting or painting. Each is marked measured or inferred, because a production build of React records no render times.

  4. It hands you the report

    You get the badge and panel, a report in code, web-vitals attribution, or attributes on the OpenTelemetry INP event.

  • Production React times no renders

    There the blame rests on counts and is marked inferred. A profiling build of React turns it into a measured blame.

  • Some browsers see less

    Event Timing's interactionId is required: Chromium 96, Firefox 144, Safari 26.2. Long Animation Frames evidence is Chromium 123 and later only.

  • Quiet interactions get no report

    After the page's first input, an interaction that paints in under 16 ms sends the browser no Event Timing entry, however heavy the render after it.

  • You can send a wrong one back

    If it names the wrong component, or a slow interaction gets no report, open an issue with the form built for it.

Install

Add the package, then the setup for your framework, and restart the dev server. Both setups are development-only by default.

Production needs an explicit opt-in. React Router, Remix, TanStack Start, Astro and webpack have setups of their own in the install guide.

Questions

Does it change my app?

The Vite plugin and the Next.js wrapper add an install script that runs before React, and a transform that keeps component names in production. Your components are not edited. With enabled left at its default, neither plugin adds anything to a production build.

Should I use the web-vitals route or the OpenTelemetry one?

If you already send web-vitals to Sentry or GA4, use web-vitals: it is one option on onINP. If your INP event goes through OpenTelemetry's web vitals instrumentation, Honeycomb, Elastic, Embrace or Grafana Faro, use OpenTelemetry. That route is experimental, so its names can change in a minor release.

Can I run it in production?

It is a development tool first, and production is optional. Turn it on with enabled: true and sample it with sampleRate. Its own time was 1.3 to 3.4 ms per interaction at the median on two demo scenarios, and what loads with the page is 35.8 KB gzip.

Does it send what people type?

No. target.label never reads a form field's value. The OpenTelemetry entry sends component, handler and script names and numbers only. A label that your own code builds from user data would go out as written, so check the ids and test ids you set.

Which browsers and versions does it support?

It needs Event Timing's interactionId: Chromium 96, Firefox 144, Safari 26.2. It reads react-dom 17, 18 and 19, runs with Next.js 14.2 or later, and its CI covers Vite 6.4, 7.3 and 8.3 and a build on Vite 5.

What if it blames the wrong component?

That happens, and it is how the blame gets better. Add debugGlobal: true, copy the report JSON right after the slow interaction, and open a wrong or missing blame issue on GitHub.
