# Protocol revision, 2026-10-15

This revises [protocol-2026-10-14.md](protocol-2026-10-14.md) for the five-app EF-360 benchmark. The 2026-10-14 file is kept unchanged as history. The app selection stays as set in [amendment-2026-10-15.md](amendment-2026-10-15.md). This revision is published before any scored capture. No scored capture existed when it was written.

## Why this revision exists

The frozen interaction cases were written before the adapters ran. Running the adapters showed that several frozen claims describe things the apps do not do: a panel where the app opens a page, a budget name where budgets have none, a year table where the app shows a selector, a calendar link the app rejects, a sign toggle that changes a budget's sign, and a label that is not the one written. The frozen wording was wrong about these apps. This revision rewrites those claims to what each app really does, records each change with its reason, and freezes the corrected cases before capture.

No result was seen or graded before these rewrites. They are not based on any attribution output.

## Rules applied to every case

1. Case IDs, count and order are unchanged. No case is dropped.
2. A frozen claim the app satisfies and the step can check is kept as written, and an unchecked claim gets an assertion.
3. A frozen claim the app does not satisfy is rewritten to the observable state the app really produces. The case's intent stays. A claim is never weakened where the app does satisfy it.
4. A frozen action is changed only when it cannot be performed as written, and the change is the closest action the app supports.
5. A step performs the frozen action and asserts every claim in the case.

## Readiness gates

These gates replace the single smoke gate of 2026-10-14. They are defined here before any scored capture.

- **Accuracy readiness.** Every case in the app's cases file passes when run alone in a fresh seeded context on configuration B, with zero page errors. The first accuracy run is this check. A case that fails alone is a setup failure. It is recorded with its exact cause and is not replaced, dropped or reworded after the fact.
- **Overhead readiness.** The overhead workload (below) passes in one ordered session on configurations A, B and C. Configuration B and C must show the library, and configuration A must not run library code.
- **Overhead workload.** The frozen cases in frozen order, minus any case whose claim depends on state that an earlier case in the same session leaves behind. For kresus those are C07, C17 and C21, which are removed from the overhead workload only. They stay accuracy cases and are captured alone. For the other apps, the ordered workload is the full cases file. The overhead workload for each app is written into its adapter and recorded in the manifest.

## Changes to environment and databases

- **PostgreSQL, not SQLite.** kresus and reactive-resume run on PostgreSQL 16 on 127.0.0.1 at ports 5442 and 5444. manage-my-damn-life-nextjs runs on PostgreSQL 16 on 127.0.0.1:5443, with DB_DIALECT=postgres and the upstream Sequelize migrations (14 migrations, all applied). No app runs on SQLite. The 2026-10-14 file named no database for any app.
- **Myfin on MariaDB 10.11.14** at 127.0.0.1:5451, as the task set. The upstream compose file uses MySQL 8.4, which is not used here.
- **Myfin API on port 5325** is outside the documented 5310 to 5324 range. The port is assigned in bench/apps.mjs and is not used by any other app.
- **Database roles.** Each adapter creates its own role and per-configuration databases with the superuser credentials in its state directory. The superuser is used for setup only.
